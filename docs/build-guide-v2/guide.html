Part A: Build guide

1. What you are building

1.1 Purpose in one paragraph

You are building one Google Sheet that runs cold outreach for several brands at the same time. Staff add leads to a brand's tab. The system writes a personal email draft for each lead with AI, waits until someone approves it, sends it from one of that brand's Gmail mailboxes at a slow, human pace, notices replies and bounces, and emails a report twice a day. The same sheet sends WhatsApp template messages through Meta's official Cloud API and records delivery, read receipts and replies. A small password-protected website shows all of it as charts. Nobody in daily operation needs to open code, a terminal or a cloud console.

Every tab, log and report is keyed by a brand code that never changes once chosen.

1.5 What the owner sees day to day

  1. Around 10:00. The morning report arrives at info@99marketingservices.com: replies from the last 7 days (brand, who, name, phone, reply time, when we emailed, and whether it is new since the previous report), sends by brand, and failures. Auto-replies and bounces are listed separately, not counted as replies.
  2. Through the day. Staff paste leads into the brand tabs: Person / Company (A), Email (B), optional Details (C), Phone (O). Within one or two sender runs Subject (auto) (D) and Email draft (auto) (E) fill in and Email status (F) says Generated.
  3. Approving. Someone reads the drafts and types Yes in Approve email (Yes) (J); the sender then picks those rows up one at a time per brand, within the Limits. For WhatsApp, they set Send WhatsApp (Yes) (P) and WhatsApp consent (Yes) (Q).
  4. Watching. The sheet's Dashboard tab shows counts per brand. The Vercel dashboard shows the same as charts, refreshed every 60 seconds, plus the latest WhatsApp replies with masked phone numbers (for example 9198****233).
  5. Around 18:00. The evening report repeats the 7-day view and adds today's numbers and tomorrow's plan.
  6. When something is off. The report or dashboard shows a plain reason (invalid_grant on a mailbox, Failed: ... on a WhatsApp row, a brand Off in Limits); chapter 19 maps each to its fix.

In a hurry, the manager selects the row and chooses AUTOMATION → Mail → Send mail to selected rows. Sending hours, the brand gap and brand caps are skipped; On/Off in Limits, Do Not Contact, "already sent" and the mailbox daily limit still apply. Rows with no draft get an AI draft sent without review, and the confirmation dialog says so (chapter 7).

1.7 A message's life: WhatsApp

The same lead's WhatsApp, phone 98765 43210 in column O. Chapter 11 has the detail.

  1. Ready. Staff set P = Yes and Q = Yes. Without consent the row is never sent.
  2. Sent. The trigger waTick runs every 5 minutes while Automatic WhatsApp is On. Per brand it checks: channel On in Limits, WhatsApp hours, daily/hourly allowance and gap, WhatsApp Setup complete (Phone Number ID, WABA ID, template). The number becomes 919876543210 via Default country code 91. If WhatsApp live sending is No, only WhatsApp test numbers are sent to. POST /{phone-number-id}/messages sends the template with the logo header (uploaded once, reused by media id). At most 30 messages per run across all brands (Apps Script's 6-minute limit). R = Sent, S = sent at, T = Meta message id, and a line goes to WhatsApp Log.
  3. Delivered / Read. Meta posts status events to the web app's doPost; the row whose T matches gets U = Delivered, later Read. Labels only move forward.
  4. Failed instead. U = Failed: <reason>. The most common is error 131049, Meta's per-user limit on marketing messages; not a system bug and not fixed by resending.
  5. Reply. The script matches Asha's number (or the replied-to message) to the lead: V = Yes, W = time, X = first 500 characters, plus a WhatsApp Replies row. Duplicate deliveries are ignored by message id. A reply of STOP adds the number to Do Not Contact.
  6. Dashboard. The reply and the sent → delivered → read → replied funnel appear on the Vercel site within about a minute.

Because the business number was already connected to another Meta app, every webhook event is also forwarded unchanged to that app's previous receiver (Script Property WA_FORWARD_URL), so its auto-replies keep working (11.6).

Three loops: the mail loop (sheet → Cloud Run → Gmail → sheet), the WhatsApp loop (sheet → Apps Script → Meta → webhook → sheet) and the read-only visibility loop (sheet → web app feed → Vercel → browser).

2.3 Why this split

  • Apps Script is free, signed in to the sheet, and can serve a public HTTPS endpoint, but one execution runs at most 6 minutes and triggers and outbound HTTP calls have daily quotas. It suits menus, small WhatsApp batches (30 per run) and a fast webhook, not bulk AI drafting or holding mailbox secrets.
  • Cloud Run jobs run ordinary Python with no 6-minute ceiling (task timeout 30 minutes), can be unit tested, and read secrets from Secret Manager, out of sight of sheet users. A job, not a service, because nothing needs to listen for requests.
  • Gmail API instead of SMTP. One OAuth sign-in per mailbox, no stored passwords, narrow scopes (gmail.send, gmail.metadata), and the same sign-in lets the reports read thread headers.
  • WhatsApp in Apps Script. One Graph API call per message, the webhook must be public anyway, and replies must land in the sheet; no second always-on service.
  • Dashboard on Vercel, reading a feed. It never touches Google credentials and holds one read-only key, so a dashboard fault can never stop mail or WhatsApp.

2.4 One 5-minute sender run, step by step

  1. 10:35:00. Scheduler calls the Cloud Run Admin API to run email-sender-master.
  2. Lock. main.py takes the Firestore document run_lock in a transaction. If another run holds an unexpired lock, it prints "Another unified main.py run is already active. Exiting." The lock expires after 30 minutes, so a crashed run cannot block sending forever.
  3. Send-now queue first (app/send_now.py); each queue line gets a result and a done time.
  4. Round-robin. The brand order starts one place later than last time (next_start_index).
  5. Per brand (BrandRunner.process): check tabs exist; read Mail Control, Mail Log, mailbox rows, leads and Do Not Contact; stop if Emergency stop is Yes (whenever Mail On = No in Limits); sync mailbox counts; draft up to 20 rows; take the first approved row; run the checks in 1.6; choose a mailbox; send one email; write back.
  6. Advance round-robin, release lock, print a summary such as marketing: processed=True generated=3 sent=True skipped=- errors=0 (in Cloud Logging).

A typical run takes well under a minute; heavy drafting takes longer, which is why the lock lasts 30 minutes and the bulk rewrite tool stops after a 22-minute budget. Chapters 8 and 18–20 cover the code, retries and recovery.

3.2 OpenAI and WhatsApp costs

OpenAI (estimate only). One draft sends roughly 800-1,200 input tokens and gets back a subject and body of about 150-250 words; gpt-5-mini also bills hidden reasoning tokens as output, and about 1 in 10 drafts needs one rewrite. That is roughly 1 million input and 0.6-1.2 million output tokens per 1,000 drafts. At $0.25 per million input and $2 per million output tokens, the estimate is about $1.50-3.00 per 1,000 drafts. The rewrite of 1,099 queued drafts on 30 Sep 2026 cost a few dollars. Put a monthly usage limit on the OpenAI project.

WhatsApp. Meta charges per message by template category (marketing, utility, authentication) and recipient country; marketing templates to Indian numbers are typically under ₹1 per delivered message, and replies inside the 24-hour customer-service window are treated differently. Rates change often: check current Meta pricing in WhatsApp Manager. Meta also limits a new number to a few hundred unique contacts a day at first, and may refuse marketing templates to people who received many recently (error 131049).

3.3 Decisions to make first

  1. Brands and codes. Short, stable codes (SB, 99M, 99S, PE, SC) used as tab names, Mail Control/Log suffixes and log keys, plus a brand id (shaadi, marketing, ...) for the config folder.
  2. Mailboxes per brand. Several low-volume mailboxes beat one busy one. Plain Gmail is free but cannot have SPF/DKIM/DMARC for gmail.com; Workspace on your own domain is better at scale. Both work.
  3. Sending hours and days. The live sender runs 10:00-17:55 Monday to Saturday IST (*/5 10-17 * * 1-6); each brand's Limits row can narrow that (default 10:00-18:00). WhatsApp has its own row.
  4. Daily and hourly caps. Per brand (Limits) and per mailbox (Mailboxes); a send must pass both.
  5. Warm-up. New mailboxes start at 3 a day and rise with clean sending days (stages in 5.9).
  6. Approval policy. Review every draft (default), or let trusted staff use "send selected rows", which can send unreviewed AI drafts.
  7. Template wording. Each brand's WhatsApp template must be approved by Meta (hours to days), so decide early. Email tone per brand goes in brand_facts and the angles in email_generator.py.
  8. Consent rules. Who counts as consented to WhatsApp, recorded in column Q (chapter 15).
  9. Report recipient and times. Live: info@99marketingservices.com at 10:00 and 18:00 daily.
  10. Who has access. Sheet editors (can approve and send), Apps Script editors (see Script Properties: owner only), Google Cloud roles (owner only), Meta admins, Vercel and GitHub members, and who knows the dashboard password.

4. Phase 1: Google Cloud project

Phase 1 builds what the mail sender and the two daily reports need: one project, the APIs, a service account, Firestore for locks, an image registry, two secrets and a scheduler. You do it once; afterwards the only regular Cloud work is deploying (bash go_master.sh sender) and connecting mailboxes (Phase 2). WhatsApp and the dashboard feed run in the sheet's Apps Script project and need no Cloud setup.

4.1 Work in Cloud Shell

Every command in this chapter runs in Cloud Shell, the free terminal in the Google Cloud console (the >_ icon, top right). It has gcloud, python3, git, tar and docker and is signed in as you. Only your home folder (~, 5 GB) survives between sessions.

Habits that avoid problems met during the build (fix log 20.12):

Habit Why
Click inside the terminal before typing. Otherwise keystrokes go to the console page and a paste silently goes nowhere.
Never paste more than about 1.5 KB at once. The terminal freezes on large pastes. Upload a file instead.
Move code in as one .tgz bundle. On your computer: tar -czf mail.tgz mail from the repo root. In Cloud Shell: More (three dots) → Upload. It lands in ~.
Watch for _(1) names. Re-uploading an existing name saves mail_(1).tgz; extracting mail.tgz would deploy yesterday's code.
Extract into a fresh folder. Old files left in ~/mail get built into the image.
Set the project at the start of each session. go_master.sh reads it from gcloud config get-value project.

The safe sequence for every upload:

gcloud config set project zoho-mail-automation-502409   # your project ID
ls -lt ~/*.tgz | head -3          # newest first: is it mail.tgz or mail_(1).tgz?
rm -rf ~/mail                     # fresh folder, never merge into an old one
tar -xzf "$HOME/mail_(1).tgz" -C ~   # quote the name: ( ) are special to bash
rm -f ~/mail.tgz ~/mail_\(1\).tgz # delete the uploads so the next upload keeps its name
cd ~/mail && ls                   # expect main.py, app/, go_master.sh, tools/ ...

Use tar -tzf <file> | head first if you are not sure whether the bundle contains a top-level mail/ folder.

A session closes after roughly an hour without input, and docker pull in Cloud Shell can stall on large images, so every deploy script builds with Cloud Build (gcloud builds submit).

4.7 Secret Manager

Two secrets, created once and then only given new versions; the jobs read latest, so a new version applies from the next run with no redeploy.

OpenAI key:

rm /tmp/empty.json

Rules for secrets:

  • Never print a secret to "check" it; print names, counts or true/false only (5.6). If a value is exposed, rotate it (chapter 16).

  • Keep few active versions (6 are free per billing account; every mailbox connection adds one). After a successful connection, disable or destroy older versions:
gcloud secrets versions list gmail-oauth-bundle --format='table(name,state,createTime)'
gcloud secrets versions destroy <OLD_VERSION_NUMBER> --secret=gmail-oauth-bundle

Never destroy the newest version or one a job is pinned to. versions disable is reversible.

5. Phase 2: Gmail senders and OAuth

Each sending mailbox signs in once and hands the system a long-lived refresh token; no Gmail password is stored. Each run trades it for a short-lived access token and sends through the Gmail API. The live mailboxes are listed in 1.2.

5.1 OAuth consent screen

Google Cloud console → APIs & Services → OAuth consent screen (on newer consoles: Google Auth Platform → Branding / Audience / Data access).

  1. User type: External (senders are gmail.com accounts). Internal only works when every sender is in one Workspace domain you own.
  2. App name (for example "Outreach Mailer"), support email and developer contact: your own address. Mailbox owners see the app name when signing in.
  3. Scopes (Data access → Add or remove scopes), exactly these two: - https://www.googleapis.com/auth/gmail.send — send only; cannot read. - https://www.googleapis.com/auth/gmail.metadata — headers and labels only (From, Subject, dates, X-Failed-Recipients), for the reports' reply and bounce search. No bodies, which is why reports never show reply text.
  4. Test users (Audience): add every sending address.

Testing versus production matters most on this screen:

Publishing status Effect
Testing Only listed test users can sign in (others see "access blocked"). Refresh tokens expire after 7 days. A week after connecting, the mailbox's sends fail with invalid_grant and the reports say "OAuth invalid_grant; mailbox needs authentication repair".
In production, not verified Anyone can sign in after a "Google hasn't verified this app" warning (Advanced → Go to (unsafe)). Refresh tokens do not expire on a timer. Unverified apps are capped at 100 users, far above this system's needs.

Use In production for unattended running; Testing means reconnecting every mailbox weekly. The giveaway for Testing: invalid_grant on every mailbox about seven days after each was connected.

5.2 OAuth client (Desktop app)

5.4 How connect_gmail.sh works

Run it in Cloud Shell from the unpacked mail/ folder: bash tools/connect_gmail.sh name@gmail.com.

  1. Normalise the address (lower case, trimmed). Project defaults to zoho-mail-automation-502409 (override with PROJECT=<PROJECT_ID> bash tools/connect_gmail.sh …).
  2. Read the bundle into a private temp folder (umask 077, mktemp -d, removed by a trap). Nothing is printed.
  3. Pre-checks: the secret is a non-empty JSON object; one entry has client_id and client_secret (the template); the address contains @. If already present it asks "Replace its sign-in (use this to fix invalid_grant)? [y/N]".
  4. Build the sign-in link: client_id, redirect_uri=http://localhost:8765/, both scopes, access_type=offline, prompt=consent (forces a fresh refresh token), login_hint=<address>, a random state, and PKCE (code_challenge = SHA-256 of a random verifier, method S256).
  5. You open the link, pick the right account (Use another account if needed), pass the unverified-app warning, and tick both permissions.
  6. Google redirects to http://localhost:8765/?state=…&code=…, which shows This site can't be reached (nothing listens on your computer). Expected: copy the whole address and paste it at the prompt.
  7. Checks on the pasted address: error= (e.g. access_denied) stops; a mismatched state stops ("That address is not the one from this sign-in").
  8. Exchange the code with the PKCE verifier; Google's refusal text is shown without any token.
  9. Verify: a refresh_token is present (otherwise remove the app at myaccount.google.com/permissions and retry); both scopes granted (otherwise "Permission not granted: gmail.metadata. Tick both boxes"); users.getProfile returns the same address (otherwise "You signed in as X, not Y"). Any failure ends with "nothing changed".
  10. Write the entry (template fields minus old token, refresh_token, expiry; plus new refresh token, token_uri, scopes) as a new secret version. It prints only "Signed in as … Mailboxes in the bundle: N."
  11. Check the jobs: prints a NOTE if email-sender-master, email-report-morning or email-report-evening mounts a bundle version other than latest.

The resulting bundle, with placeholders:

{
  "linkwithmarketing@gmail.com": {
    "client_id": "<CLIENT_ID>.apps.googleusercontent.com",
    "client_secret": "<CLIENT_SECRET>",
    "refresh_token": "<REFRESH_TOKEN>",
    "token_uri": "https://oauth2.googleapis.com/token",
    "scopes": ["https://www.googleapis.com/auth/gmail.send",
               "https://www.googleapis.com/auth/gmail.metadata"]
  },
  "linkwithmarketing3@gmail.com": { "...": "same shape" }
}

Keys are lower-case addresses. The job mounts the secret read-only (GMAIL_TOKEN_BUNDLE_FILE); credential_store.load_credentials builds Credentials.from_authorized_user_info(entry, scopes). Refreshed access tokens are not written back; the refresh token is reused next run.

The script reads answers from /dev/tty, because its Python part runs from a heredoc (fix log 20.10), so it must run in an interactive terminal; answers cannot be piped in.

5.5 Where the address must also be listed

A refresh token alone does not make a mailbox send. limit_manager.select_mailbox uses a mailbox only if:

  1. It is in the brand's list: gmail_accounts in config.json, or a row in hidden Mail Control XX (rows 13–60), created by Add a sending mailbox (with_sheet_mailboxes).
  2. Enabled = Yes and Paused ≠ Yes in the Mailboxes tab.
  3. Sent today (counted from Mail Log XX) is below its daily limit, and sent this hour below its hourly limit.
  4. The address is a key in the bundle.
  5. The minimum gap since its last send has passed.

It picks the lowest share of daily limit used, then the one that sent longest ago. A mailbox failing check 4 is skipped silently, so an unconnected mailbox never causes an error.

5.7 Reconnecting after expiry or revocation

A refresh token dies when: the app is in Testing and 7 days have passed; the owner changes the Google password; the owner removes the app at myaccount.google.com/permissions; the account is disabled or suspended; or it was unused for about six months.

Fix: bash tools/connect_gmail.sh that@gmail.com, answer y to "already connected. Replace its sign-in", sign in again.

Meanwhile each attempt marks a row Failed (Send failed: …invalid_grant…), and since failures do not count toward sent today, the broken mailbox keeps being picked. So at the first invalid_grant: set Paused = Yes in Mailboxes, reconnect, set it back to No, and reset the failed rows (F to Generated keeps the draft; clearing D:F gets a new one).

5.9 Mailbox hygiene

  • One mailbox, one brand, never a personal inbox.
  • Look like a person: real display name, profile photo, a short signature for manual mail. The automation's signature deliberately has no website link (fix log 20.7).
  • 2-step verification on, with recovery phone and email; keep sign-ins in a password manager.
  • Warm up. Start at 3 a day and 1 an hour and raise slowly while bounces stay at zero. Reference ramp in limit_manager.stage_for: Stage 1 = 3/day, 1/hour; Stage 2 (3+ clean days) = 5/2; Stage 3 (7+) = 8/2; Stage 4 (14+) = 12/3; Stage 5 (21+) = 15/3; Established = 20/4. Warm-up stage is a label only (copied into the Mail Log); the enforced limits are the Daily and Hourly limit numbers you type, so raise those yourself.
  • Send a few emails by hand in the first week, reply to what comes in, and check the Sent folder now and then. More in chapter 14.

6.11 What "Set up / repair tabs" does

ccSetup is safe any time and never deletes data. In order:

  1. Renames earlier-version tabs (Dashboard, Brands, Settings, Mail, WhatsApp, SMS, WA Templates, SMS Templates, Send Log, Tasks, Untitled) to OLD - <name> unless they are the current Dashboard/Settings (A1 note), hiding them at the end (one tab must stay visible).   3. Limits and Mailboxes: filled only if empty; dropdowns re-applied.
  4. Do Not Contact, WhatsApp Setup, WhatsApp Log, WhatsApp Replies: created if missing, headers rewritten.

6.12 Formatting rules that prevent bugs

  • Plain text (@) for log tabs, phone (O), IDs (K, T), time columns and Limits G:H; otherwise 2026-09-30 10:00:00 becomes a date number, +9198… a formula error, long numbers 9.19E+11. Before pasting phones, select column O → Format → Number → Plain text.
  • Paste values only (Ctrl+Shift+V) so formats and dropdowns stay.
  • Yes/No exactly. yes is compared case-insensitively after trimming; Y, yes please or a tick box are "not yes".
  • System dates are text yyyy-mm-dd HH:MM:SS, except N (dd-Mon-yyyy HH:MM). Do not reformat.
  • No merged cells, hiding filters or sorting in brand tabs: send-now and the webhook address rows by number.
  • Protections (optional): Show a warning when editing on D:I, K:N, R:X and the hidden tabs stops accidental typing without blocking scripts. Use "Restrict who can edit" only with the service account on the list.

6.13 The owner's rules

Standing instructions for anyone, human or program, changing the sheet:

  1. Never overwrite existing leads. Append below the last row; imports merge by email and keep rows only in this sheet.
  2. Never bulk-overwrite statuses or approvals (F, J, R, webhook columns). The only sanctioned bulk changes: regenerating queued drafts (D:E only, backup first) and resetting specific Failed rows at the owner's request, backed up to Old drafts (backup).
  3. Never overwrite formulas in Dashboard, Mailboxes H:I or Mail Control; change Limits and Mailboxes values instead.
  4. Never delete log rows (Mail Log, WhatsApp Log, WhatsApp Replies, Do Not Contact); they prevent double sends.
  5. Back up before any script change to many rows, state how many rows will change, test on one row first.

7. Phase 4: Apps Script (the sheet's brain)

The control sheet "Automation Control Center" has one Apps Script project bound to it (Extensions → Apps Script). The script does four jobs:

  1. It builds and repairs the tabs, and adds the AUTOMATION menu.
  2. It lets a person act on rows by hand: send mail now, send WhatsApp now, add a mailbox.
  3. It sends WhatsApp on a 5-minute timer, inside the sheet, at no cost.

Mail is not sent from the script: Apps Script stops any run after 6 minutes, and drafting plus sending for five brands can take longer. Mail runs on Cloud Run (chapter 8); the sheet only queues rows and starts the job.

7.5 "Send mail to selected rows" in detail

The normal sender is deliberately slow (one email per brand per run, 25-minute gap). This item emails a few hot leads right now.

In the sheet (mlSendSelected)

  1. The active tab must be a brand tab (SB, 99M, 99S, PE, SC). If not: "Open a brand tab … and select the lead rows first."
  2. Several blocks (Ctrl-click) are allowed. mlSelectedRows_ ignores rows 1–2; more than 25 rows is refused.
  3. If the brand's Limits Mail row has On = No, nothing is queued.
  4. It reads Do Not Contact column A and the Pending lines in the hidden Mail Send Now tab (created if missing).
  5. mlSendCheck_ checks each row: valid email, not already Sent, not in Do Not Contact, status not Unsubscribed or Bounced, not already queued. Rows with no subject or draft are counted.
  6. A confirmation lists up to 8 rows and warns: "N row(s) have no draft: the AI writes one and it is sent WITHOUT your review. Sending hours and the gap are ignored. Mailbox daily limits still apply."
  7. It appends Requested at | Brand | Row | Email | Requested by | Pending | | (A:H, all text) per row, calls SpreadsheetApp.flush(), then mlStartMailJob_().
  8. Success: "Sending started. The rows turn "Sent" in about 2 minutes." Failure shows the HTTP code and Google's message; the lines stay Pending for the next scheduled run.

In the job (mail/app/send_now.py) the queue is processed first (8.5). Each line ends with Status = Sent, Skipped or Failed, a Result and Done at, which Show send-now results reads back.

Why a queue tab rather than calling the job with row numbers? A running job holds the run lock, so a direct call would be refused; a Pending line survives failures until some run handles it; and the tab is an audit log of who asked for what.

  if (e && e.parameter && e.parameter['hub.mode']) return waVerifyWebhook_(e.parameter);

On Verify and save, Meta sends GET <callback>?key=…&hub.mode=subscribe&hub.verify_token=…&hub.challenge=<number>. waVerifyWebhook_ returns the challenge as plain text only if the mode is subscribe, the verify token equals WA_VERIFY_TOKEN and key equals WA_HOOK_KEY (at least 20 characters); otherwise forbidden. A JSON reply or a missing key gives "The callback URL or verify token couldn't be validated" (20.3).
  • Dashboard feed. Vercel's server calls GET <exec URL>?key=<DASH_KEY>; a wrong key gets {"error":"unauthorized"}. The key is checked before the cache, so a cached snapshot never reaches an unauthenticated caller.
  • Caching. A snapshot reads every brand tab and log (a few seconds), and the dashboard refreshes every minute. CacheService keeps it 30 seconds under key dash. Values of 100 KB or more cannot be cached, so only answers under 95,000 characters are cached. Errors (snapshot failed: …) are never cached.

doPost(e) in WhatsApp.gs receives Meta's events (details in 11.5):

  1. Always build the reply ok (Meta retries without a fast 200, and an error would tell a stranger the URL is live).
  2. If ?key= does not equal WA_HOOK_KEY, return ok and do nothing.
  3. Take the script lock (up to 20 s), parse the body, apply it. Errors are logged, never thrown.
  4. If WA_FORWARD_URL is set, POST the raw body there too, so the older bot on the number keeps working.
  5. Return ok.

Versions: why the URL stays the same. A deployment points to one frozen version; the /exec URL belongs to the deployment. So:

  • Menu functions and triggers run the latest saved code.
  • The web app (doGet, doPost) runs only the deployed version. After any change affecting them: Deploy → Manage deployments → pencil (Edit) → Version: New version → Deploy. The URL is unchanged, so Meta and Vercel need no update.
  • Do not use Deploy → New deployment for an update: it creates a second URL.
  • The Test deployments /dev URL needs a logged-in editor; Meta and Vercel can never use it.

The live deployment moved to version 3 when the feed gained the WhatsApp fields (20.16). Write the version number and date in the deployment description each time, so "which code is live?" has an answer.

8.4 One run in full detail

Cloud Scheduler (*/5 10-17 * * 1-6 IST) ──POST──> Cloud Run job email-sender-master
  main.py
   ├─ take Firestore lock  automation_state_master/run_lock  (30 min)   ── held? → print & exit
   ├─ send-now queue (Mail Send Now, max 25 lines)                      (8.5)

   │     BrandRunner.process()  → at most ONE normal email
   ├─ advance round-robin index

1. Lock. firestore_lock("run_lock") runs a Firestore transaction on automation_state_master/run_lock. If locked_until is in the future, the job prints Another unified main.py run is already active. Exiting. and ends normally. Otherwise it writes {owner: <host>-<random>, locked_until: now+30min} and at the end deletes the document if still the owner. A crashed run blocks sending for at most 30 minutes, matching the 1,800-second task timeout, so a run never outlives its lock.

2. Send-now queue (8.5). Skipped for --dry-run, --generate-only and --brand. An error is logged (send-now queue failed: …) and the run continues.

3. Brand order. round_robin.ordered_brand_ids() rotates BRAND_ORDER from next_start_index, which moves up by one after a real run.

4. Each brand: BrandRunner.process(). A crash in one brand is caught and reported as <brand> failed: …; the others still run.

  1. Tabs. sheet_ids() checks the control, lead, log and suppression tabs exist.
  2. Settings. 'Mail Control XX'!A2:C10 into a dict; blanks fall back to config.json.
  3. Reads. Mail Log A2:I, mailbox rows A13:M60, leads A3:L, Do Not Contact A2:C.
  4. Mailboxes. with_sheet_mailboxes adds Mail Control A13:A60 addresses missing from gmail_accounts. read_mailboxes_from_rows builds a Mailbox per row (limits from D/E or defaults; sent_today/sent_this_hour counted from the Mail Log).   6. Sync counters. Recalculated Sent Today / Sent This Hour → F:G (one batch).

If anything was drafted, leads are re-read.
  8. Pick the row. _first_approved_row: first row with J Yes and F Generated, Approved or Scheduled; else No approved lead is ready.
  9. Brand caps. brand_cap_reason counts today's and this hour's Sent log lines against Limits D/E (blank or 0 = no cap): Brand daily limit reached (N per day).
  10. Brand gap. _remaining_sheet_gap_minutes: newest Sent time plus the gap; if still ahead, Brand send gap active: N minute(s) remaining.

    Check F H
    Email invalid after normalization (spaces/commas removed) Skipped Invalid email address
    Subject or body blank Scheduled Approved row has blank subject or body
    In Do Not Contact Unsubscribed Recipient suppressed
    Already Sent by this brand (Mail Log) Skipped Recipient already contacted by this brand

Pace. One email per brand per run plus the gaps give a human pace (about 19 a day per brand at most, 14.1). In practice mailbox daily limits are the cap: SB with five mailboxes at 3 each sends at most 15.

8.5 The send-now queue (app/send_now.py)

process_queue reads 'Mail Send Now'!A2:H, keeps F = Pending lines (at most MAX_PER_RUN = 25) and groups them by brand. For each brand, SendNow.run:

  1. Reads settings. If Emergency stop = Yes, every line is Skipped: Mail is OFF for this brand (Limits tab: Mail On = No).
  2. Reads the Mail Log, mailbox rows (plus sheet-added mailboxes) and Do Not Contact.
  3. For each line, pausing PAUSE_SECONDS = 3 between lines so a burst does not look like a bot: - Re-reads A<n>:L<n>. check_row: no valid email / Row changed since it was selected (email is different) - select it again / Already emailed by this brand / In Do Not Contact. - Domain check. - pick_mailbox: least-used, enabled, not paused, connected, under its daily limit (hourly limit and gaps ignored). Else All mailboxes reached their daily limit (or are paused/disconnected). - A skip writes Send now skipped: <reason> to H, except "Row changed", so the wrong row is not touched. - No draft: the AI writes one, D:F saved as Generated, sent without review. AI failure: F Failed + OpenAI generation error: …, queue line Failed. - Sends and records as a normal send with gap 0. A blank J becomes Yes (send now). Mailbox counters rise in memory for the next line.
  4. Writes each line's F:H = status, result, done-at.

It ignores hours, brand gap, brand caps and the hourly limit; it respects Mail On, Do Not Contact, "already emailed", the domain check and mailbox daily limits. Because a send-now email is logged, the brand's normal send in the same run usually waits for the gap. That is intended.

8.7 Rewriting queued drafts (app/regenerate.py)

When drafting rules change, drafted-but-unsent rows keep the old text. regenerate rewrites them.

  • Which rows (needs_regeneration). Valid email, subject and body present, status Generated / Approved / Scheduled, and the body contains "\nWebsite:" (the old signature line). Rewritten rows no longer match, so the job can be stopped and rerun at any time. For a future style change, set OLD_FORMAT_MARK to something only old drafts contain.
  • What changes. Only D and E; status and approval stay, so an approved row is sent with the new text.
  • Backup. A hidden tab Old drafts (backup) (Backed up at, Brand, Row, Email, Old subject, Old draft) is created if missing, and each old subject and draft is appended there before D:E is overwritten.
  • Safety. The row is re-read after the AI answers; if sent or changed meanwhile, it is left alone. An AI failure keeps the old draft (kept old draft (…)).
  • Lock and budget. main.py --regenerate-drafts holds the sender's Firestore run lock, so no email goes out half-rewritten; if the sender holds it, it prints The sender is running right now - try again in a minute. The loop stops after TIME_BUDGET_SECONDS = 22*60 or --limit drafts, then prints Some drafts are left (time or --limit reached). Run the same command again to continue.
  • Rounds of 120. go_master.sh regen runs --regenerate-drafts --limit 120, reads that execution's logs, and repeats (up to 15 rounds, 1,800 drafts) while the output says "Run the same command again". It waits 60 s and retries if the sender held the lock.
  • regen-preview adds --dry-run: per brand, the count to rewrite plus one sample draft. Nothing is written.

Rounds are small, and one OpenAI client is cached per key (_client()), because a client per draft ran the 512 MiB job out of memory (20.5).

8.8 Sheets retries and error handling

execute_with_retry(request) in sheet_client.py:

RETRY_STATUSES = {429, 500, 502, 503, 504}
RETRY_WAITS = (2, 5, 10)  # seconds between attempts (4 attempts in total)

def execute_with_retry(request, waits=RETRY_WAITS, sleep=time.sleep):
    for attempt in range(len(waits) + 1):
        try:
            return request.execute()
        except HttpError as error:
            status = getattr(getattr(error, "resp", None), "status", None)
            if int(status or 0) not in RETRY_STATUSES or attempt == len(waits):
                raise
        # ConnectionError / TimeoutError / OSError: same, re-raised on the last attempt
        sleep(waits[attempt])
# abridged
Call Retried? Why
get, spreadsheet_metadata / sheet_ids Yes Reads are safe to repeat
update, batch_values Yes Fixed values to fixed cells; repeating gives the same result
append No If the first attempt applied but the answer was lost, a retry adds the row twice (double-counting a send)
batch_update (add a tab, etc.) No Structural changes such as addSheet fail or duplicate when repeated

Other errors (403, 400, 404) are raised at once. The retry costs at most 17 seconds per call.

Two kinds of failure:

  • The AI failed (timeout, 429 quota, missing key, persistent spam wording): shown on the row as F Failed, H OpenAI generation error: <text>. The subject is still blank, so the row is drafted again next run.
  • Saving failed (Sheets down longer than the retries): the row is left untouched and the run notes row N: draft not saved (HttpError); will retry (20.9).

Failed reads in a real run raise; that brand is reported failed and the others continue. In --dry-run a failed read is noted and treated as empty.

9. Phase 6: AI email drafting

Every lead row with an email address but no subject or draft gets a personal first-contact email written by OpenAI. The code is mail/app/email_generator.py (about 270 lines), called from brand_runner.py during the normal 5-minute sender run. This chapter covers how a draft is built, checked and saved, and how to change the style without hurting deliverability.

9.1 Why every draft must be different

Mail filters compare messages across many mailboxes. When several new Gmail accounts send hundreds of emails with the same structure (first sentence, paragraph shape, call to action, sign-off), filters treat it as a bulk campaign and move it to spam. Changing only the name is not enough, because filters use "fuzzy" text fingerprints.

So the system never asks the AI for "an email". Python first picks a random brief: opening style, brand angle, call to action, greeting, word range and opt-out sentence. The AI writes a short note following that brief. Two leads rarely get the same combination, and even then the model phrases it differently.

The model may use only approved brand facts (brand_facts in each mail/brands_master/<brand>/config.json) and the lead's Details column. It never invents clients, numbers, years, awards or locations.

9.7 One rewrite, then fail

brief = pick_brief(brand, person_name, rng, details)

problems = spam_problems(subject, body)

    subject, body = _ask(client, runtime, brand, _input(brief, person_name, details, "; ".join(problems)))
    still = [p for p in spam_problems(subject, body) if p != "exclamation marks"]
    if still:
        raise ValueError("Draft kept spam-risk wording (" + "; ".join(still) + "); will retry next run")
  • The rewrite uses the same brief, so the model only fixes the named problems.
  • Exclamation marks are tolerated on the second pass because _tidy replaces every ! with ..
  • If it still fails, only the error is written: F = Failed, H = OpenAI generation error: Draft kept spam-risk wording (...). The next run tries a new brief (a few times per thousand drafts in practice).

No loop: each attempt costs money, and a model failing twice on one brief is usually stuck on a phrase the brief invites. A fresh brief next run is cheaper.

9.10 The "no details" problem and its fix

Rows with empty Details once got drafts opening "I didn't see any details about your business, but..." or "Your profile caught my eye", from detail openings 0 and 4 (20.6). The fix has four layers:

  1. pick_brief removes openings 0 and 4 when Details is blank.
  2. _input adds for blank Details: Nothing is known about this recipient. Do NOT say that, do NOT mention details, a profile, their business or anything you 'saw' or 'noticed' about them. Write a short general note that fits anyone.
  3. didn't see any details, did not see any details, no details and your profile caught are in SPAM_PHRASES: banned in the instructions and caught by spam_problems.
  4. One rewrite, then fail (9.7).

test_no_details_brief checks it: 30 blank-details briefs never contain a detail opening, the prompt contains "Nothing is known about this recipient", and spam_problems flags "I didn't see any details about you."

9.14 Cost control

10.1 How replies are detected

Each send writes the Gmail message id to the brand's send log (column E). For each log row with result Sent, the report job:

  1. Opens the mailbox. gmail_service(brand, sender) uses the stored token and calls users.getProfile; a different signed-in address stops that mailbox (OAuth profile does not match configured sender). invalid_grant becomes the warning "OAuth invalid_grant; mailbox needs authentication repair".
  2. Finds the conversation. users.messages.get(id, format="minimal") gives the threadId; sends are grouped by (mailbox, thread).
  3. Reads thread headers only. users.threads.get(format="metadata", metadataHeaders=[From, Subject, Auto-Submitted, X-Autoreply, X-Autorespond, X-Failed-Recipients]). The gmail.metadata scope suffices; bodies are never read.
  4. Classifies each message in report_core.replies_in_thread:
Test Result
Label SENT, DRAFT, SPAM or TRASH ignored
From one of our own sending addresses ignored
Arrived after the report cut-off ignored (counted next time)
From the lead we emailed, after our email, not automatic reply
Auto-Submitted present and not no, or X-Autoreply / X-Autorespond, or sender mailer-daemon@ / postmaster@ automatic (out-of-office, bounce)
Automatic and (X-Failed-Recipients present, or daemon sender with a subject containing failure, undeliverable, undelivered, not delivered, delivery failed, returned mail, could not be delivered, delivery has failed, rejected) and the subject does not contain "delay" bounce

A reply is linked to our most recent earlier send to that address. A bounce names the lead from X-Failed-Recipients when it matches one of our recipients, else the thread's only recipient; otherwise no lead is marked.

Limits. Only replies in the same Gmail conversation are found; a new email from another address, or a reply only to a CC mailbox, is missed. This is deliberate: guessing from other threads produced false "replied" marks.

10.3 Before sending: the domain check (mail/app/domain_check.py)

Bounces quickly damage a new mailbox, so the sender checks each lead's domain first (brand_runner.py, send_now.py):

  • Query https://dns.google/resolve?name=<domain>&type=MX (no key, no cost, 8-second timeout).
  • Status 3 (NXDOMAIN) → "email domain does not exist"; all-null MX (0 .) → "email domain accepts no mail"; no MX with Status 0 → A lookup, none → "email domain cannot receive mail".
  • The row becomes F = Skipped, H = Not sent: <reason> (would bounce).
  • Never looked up: gmail.com, googlemail.com, yahoo.com, yahoo.co.in, outlook.com, hotmail.com, live.com, icloud.com, rediffmail.com, protonmail.com, proton.me, zoho.com, aol.com, msn.com.
  • Results are cached per run. A lookup error or SERVFAIL returns "no problem" and is not cached: the check never blocks a send through its own failure.

10.6 Never twice: Firestore receipts

Gmail's send API has no idempotency key. deliver_once first creates a Firestore document in automation_report_receipts with id sha256(recipient|slot|date); create() fails if it exists, so a second execution prints already claimed; no duplicate sent. After Gmail returns an id, the receipt becomes status: sent. The message gets a fixed Message-ID: <automation-report-<key>@99marketingservices.com>.

A receipt stuck at sending means delivery is uncertain: search the report mailbox's Sent folder for that Message-ID. Do not delete the receipt and resend blindly.

11.3 The sheet side

Columns O–X, the WhatsApp Setup tab, the Settings rows and the Limits WhatsApp rows are mapped in 6.3, 6.5, 6.9 and 6.10; the token is stored by Save access token (7.7). Points specific to sending:

11.5 Reading replies: the webhook

Meta sends every incoming message and every delivery update to one HTTPS callback URL: the sheet's web app, the same deployment as the dashboard feed. Verification (doGet → waVerifyWebhook_) and the doPost key check, lock and forwarding are in 7.8. doPost then:

  • waParseWebhook_ flattens entry[].changes[].value into messages (id, from, profile name, time, type, text, context.id) and statuses (id, status, recipient, time, error code + details). waMessageText_ renders non-text messages: button titles, list replies, Reacted 👍, [image] caption, [audio].
  • waApplyWebhook_ applies them as below.

Delivery updates match the lead row whose T equals the message id. waDeliveryLabel_ never downgrades (sent (not shown) < Delivered < Read); failed always wins as Failed: <code> <details>. The webhook never changes R: R says Meta accepted the message, U what happened after.

Replies, per message:

  1. Deduplicate against the last 300 rows of WhatsApp Replies (column H) and a 6-hour cache entry wam_<id>.
  2. Find the lead (waMatchLead_): the row whose T equals context.id (the customer pressed Reply), else, across all brand tabs, the row with the same normalised phone and newest sent-at (S).
  3. Write V:X = Yes, time, text.
  4. Log a WhatsApp Replies row (Received at · Brand · Row · Name · Phone · Message · Type · Message ID); unknown numbers too, with Brand and Row blank.
  5. STOP. If the whole text (lower case, trailing dots, exclamation marks and spaces removed) is stop, unsubscribe, stop all, opt out, optout, remove me or stop messages, the phone is added once to Do Not Contact (A blank, B WhatsApp STOP reply, C time, D brand, E phone).

On first use the webhook widens brand tabs to 24 columns and writes the U:X headers.

11.6 The routing problem and the WABA override

Meta picks the destination in this order:

  1. the phone number's override (webhook_configuration.phone_number),
  2. the WABA's override for a subscribed app (webhook_configuration.whatsapp_business_account),
  3. the app's webhook (webhook_configuration.application).

Here the number was already subscribed through another Meta app ("99 Consulting Services") running an older bot, so our verified webhook received nothing (20.2). See the real destination with:

curl -s "https://graph.facebook.com/v26.0/<PHONE_NUMBER_ID>?fields=display_phone_number,webhook_configuration" \
  -H "Authorization: Bearer <WA_TOKEN>"

The fix is a WABA-level override to the sheet, plus forwarding so the old bot keeps working:

curl -s -X POST "https://graph.facebook.com/v26.0/<WABA_ID>/subscribed_apps" \
  -H "Authorization: Bearer <WA_TOKEN>" -H "Content-Type: application/json" \
  -d '{"override_callback_uri":"<WEBAPP_URL>?key=<WA_HOOK_KEY>","verify_token":"<WA_VERIFY_TOKEN>"}'

Meta verifies the URI at once with the GET handshake, so the web app must already answer it. If the number has its own override (level 1), set it on the number: POST /{phone-number-id} with {"webhook_configuration": {"override_callback_uri": ..., "verify_token": ...}}. The menu does all this (11.7).

13.1 What Indian regulation requires (DLT)

Commercial SMS to Indian numbers must go through TRAI's Distributed Ledger Technology (DLT) system, run by the operators (Jio, Airtel, Vi, BSNL each have a portal; one registration is enough).

  1. Principal Entity registration with company documents (PAN, GST or incorporation certificate, authorised signatory letter) and the operator's fee. You receive an Entity ID.
  2. Headers (sender IDs). 6-character IDs, e.g. a brand abbreviation, per category (promotional headers numeric; transactional/service alphabetic).
  3. Content templates. Every text registered with its category (Promotional, Service Implicit, Service Explicit, Transactional) and variables as {#var#}. Messages not matching a template word for word are dropped.
  4. Consent templates for Service Explicit messages.
  5. Link the telemarketer (gateway such as MSG91, Kaleyra or Twilio's India route) to your entity on the portal.

Design constraints: promotional SMS only to numbers not on the National Do Not Call registry and only in the daytime window (roughly 10:00–21:00); service messages need recorded consent; URLs must be whitelisted with the operator.

14. Deliverability playbook

Deliverability means the email lands in the inbox, not in spam and not bounced. Consumer Gmail reputation is fragile: a mailbox that sends too much too soon, sends near-identical text or hits dead addresses gets throttled, filtered or suspended, and takes weeks to replace.

14.1 Warm-up schedule per new mailbox

mail/app/limit_manager.py defines the stages and a stage_for() helper that says when a mailbox has earned the next stage (enough clean days: days with sends and no pausing failure). The sender does not call it on its own: you move a mailbox up by changing its stage in Mail Control (see 8.6). Exact values in code:

Stage Clean days needed Daily limit Hourly limit Notes
Stage 1 0 3 1 Every new mailbox starts here (Mailboxes tab, row added by Add a sending mailbox)
Stage 2 3 5 2 Also send and reply to a few emails by hand
Stage 3 7 8 2 Only if there are no bounces and some replies are arriving
Stage 4 14 12 3
Stage 5 21 15 3
Established set by hand 20 4 Type Established only for an old, healthy mailbox

The Mailboxes tab (Brand, Mailbox, Enabled, Daily limit, Hourly limit, Warm-up stage, Paused, Sent today, Last result) can set a lower limit; the lower of the two applies. Gmail's consumer hard limit is about 500 per day, but the practical cold-email ceiling from gmail.com is 20 to 30.

The Limits tab Mail row adds brand controls: Max per day, Max per hour, Minimum gap (minutes) (default 25) and sending hours (default 10:00 to 18:00). At most one email per brand goes per 5-minute run; a 25-minute gap over 8 hours caps a brand at about 19 a day.

If a mailbox's bounces exceed about 3% or Google shows a warning, follow 14.6.

14.2 Content rules enforced in code

The rules live in mail/app/email_generator.py and are enforced in code, because a model follows the prompt only most of the time.

Rule How it is enforced
No two emails alike pick_brief() picks a random opening (5 styles), angle (4 to 5 per brand), call to action (5), greeting (4 with name, 3 without), length band (60-80, 70-95 or 85-110 words) and opt-out sentence (4) per lead
Plain text, no links spam_problems() rejects http://, https://, www., .com, .in in subject or body
No exclamation marks, no bullets Rejected by spam_problems(); _tidy() also turns any ! into .
No spam words SPAM_PHRASES (free, guarantee, 100%, act now, discount, quick question, touch base, leverage, game changer, and so on) matched as whole words
Short, calm subject 2 to 6 words (7 tolerated), not mostly capitals
Never narrate missing data Phrases like "didn't see any details" and "your profile caught" are in SPAM_PHRASES; detail-based openings are used only when Details is filled (see 20.6)

The model is gpt-5-mini (env OPENAI_MODEL), strict JSON schema output (subject, body), reasoning.effort = minimal: roughly 1,000 to 1,500 tokens per draft.

14.3 List quality

  • Use only publicly listed business contact addresses or people who asked to hear from you. Never buy lists.
  • Deduplicate across brands before import; the sender also refuses leads in Do Not Contact (suppression_manager.py) or already contacted (duplicate_manager.py).
  • domain_check.py checks each non-webmail domain via Google's DNS-over-HTTPS (dns.google). NXDOMAIN, a null MX (0 .), or neither MX nor A gives Skipped – would bounce. A failed lookup never blocks sending.
  • Report-found bounces mark the lead Bounced and add it to Do Not Contact once (reply_sheet.py, mark_bounced); is_bounce() in report_core.py ignores "delayed" notices and out-of-office replies.
  • Fill the Details column (C): leads with details get a specific first line and more replies, the strongest positive signal a mailbox can earn.

14.4 SPF, DKIM and DMARC: own domain versus gmail.com

The live system sends from plain @gmail.com addresses (for example linkwithmarketing@gmail.com). Google signs with DKIM for gmail.com and owns the SPF record, so there is nothing you can publish; reputation is Google's plus the mailbox's.

On your own Google Workspace domain (recommended as volume grows), publish:

Record Host Value
SPF (TXT) @ (the domain) v=spf1 include:_spf.google.com ~all
DKIM (TXT) google._domainkey Generate in Admin console → Apps → Google Workspace → Gmail → Authenticate email; publish the TXT; then press Start authentication
DMARC (TXT) _dmarc Start with v=DMARC1; p=none; rua=mailto:dmarc@<yourdomain>; after 2 to 4 weeks of clean reports move to p=quarantine

One SPF record per domain: add other senders' include: to it. Use a separate (sub-)domain for cold outreach so problems never reach the staff domain.

Gmail's rules for all senders: SPF or DKIM, user-reported spam below 0.1% and never 0.3%. Bulk senders (5,000+ a day to Gmail) also need SPF and DKIM, aligned DMARC and one-click unsubscribe. We are far below that line but follow the same hygiene.

14.6 When a mailbox is flagged

Signs: a Gmail warning banner, "unusual activity" prompts, failing sends, invalid_grant in the report, or suspension.

  1. Mailboxes → Paused = Yes. The brand's other mailboxes keep working.
  2. Log into the mailbox in a browser and complete any security check (phone, password).
  3. Find the cause: bounces from one bad list, a changed template, a sudden limit increase.
  4. Wait three to five days, using the mailbox normally by hand (read, reply to real messages).
  5. If Google changed the password or revoked access, reconnect: bash tools/connect_gmail.sh <address> (18.8).
  6. Restart one stage lower (Stage 1 or 2) by typing the stage, then Paused = No.
  7. If suspended and the appeal fails, set Enabled = No and warm up a replacement.

15.2 Opt-out handling

Every email ends with a human opt-out sentence ("If this is not relevant, just reply and I will not contact you again").

  • Any email reply marks Replied = Yes (M, time in N); replied rows get no follow-up. Removal requests are handled by hand: add to Do Not Contact with reason Asked to stop.
  • A WhatsApp reply of just "STOP" (any case, optional full stop) is caught by waIsStop_(); the number goes once into Do Not Contact with reason WhatsApp STOP reply. "Please stop by tomorrow" is deliberately not STOP; handle such messages by hand.
  • Meta error 131050 ("recipient stopped marketing messages") sets the WhatsApp status to Opted out.
  • Do Not Contact is shared by all brands (column A email for mail, E phone for WhatsApp): one opt-out stops every brand. Never delete its rows; they prove the request was honoured.

15.3 WhatsApp opt-in rules

Meta's WhatsApp Business Messaging Policy requires opt-in before any business-initiated (template) message, and honouring opt-outs.

  • Set WhatsApp consent (Yes) (column Q) only for real consent: a form with a WhatsApp checkbox, a written request, an enquiry asking for WhatsApp contact.
  • The sender refuses rows without consent = Yes, including Send WhatsApp to selected rows.
  • Marketing templates face Meta's per-user limits (131049, 20.14); high block or report rates lower the number's quality rating and messaging limit.
  • Use test mode (Settings → WhatsApp live sending = No) until templates and consent records are checked.

  3. Bounced leads are already in Do Not Contact. Filter the rest of that import by date, check domains, delete clearly bad rows.
  4. Pause any mailbox with more than 3% bounces for a few days (14.6).

20.1 Webhook URL in the setup dialog was the test deployment

Symptom. The callback URL shown by Set up reply webhook failed Meta's verification, though it opened in the owner's browser.

Cause. ScriptApp.getService().getUrl(), called from a menu, can return the test (/dev-style head) deployment, which works only for signed-in editors. Meta calls anonymously and was refused.

Fix. Store the live /exec URL and prefer it:

// WhatsApp.gs (abridged)
var WAH = { HOOK_PROP: 'WA_HOOK_KEY', VERIFY_PROP: 'WA_VERIFY_TOKEN', FORWARD_PROP: 'WA_FORWARD_URL',
  WEBAPP_URL: 'https://script.google.com/macros/s/<DEPLOYMENT_ID>/exec' };
var url = p.getProperty('WEBAPP_URL') || WAH.WEBAPP_URL;

Copy the URL from Deploy → Manage deployments (Access Anyone) into Script Property WEBAPP_URL.

How to verify. In a signed-out private window, <WEBAPP_URL>?hub.mode=subscribe&hub.verify_token=<TOKEN>&hub.challenge=42&key=<HOOK_KEY> shows 42.

Prevention. Keep deployment URLs as configuration; test public endpoints signed out.

20.2 Meta verified the webhook but replies never arrived

Symptom. Webhook verified, messages Subscribed, yet no replies reached the sheet and Executions showed no doPost calls.

Cause. Meta delivers each event to exactly one address, in order: the phone number's override, the WABA's override per subscribed app, then the app's webhook. The number was subscribed to another Meta app, "99 Consulting Services", whose auto-reply bot got every message.

Fix. Menu Check reply webhook (waCheckWebhook) reads GET /{phone-number-id}?fields=display_phone_number,webhook_configuration, reports where messages go and, on confirmation:

  1. saves the current receiver as WA_FORWARD_URL, so doPost forwards every event and the old bot keeps working;
  2. sets the override at the level in use:
POST /{waba-id}/subscribed_apps
  { "override_callback_uri": "<WEBAPP_URL>?key=<HOOK_KEY>", "verify_token": "<VERIFY_TOKEN>" }

(or webhook_configuration.override_callback_uri on the phone number if that level was set).

How to verify. Check reply webhook prints = THIS SHEET; "Hi" to the business number appears in WhatsApp Replies within seconds and the old bot still answers.

Prevention. Check webhook_configuration before building; document which Meta app owns each number.

20.3 "The callback URL or verify token couldn't be validated"

Symptom. Meta's Verify and save failed even with the correct URL.

Cause. Three causes, each seen once: (a) doGet returned JSON or HTML, not the bare challenge; (b) the web app still served an older version without the verification branch; (c) ?key= was missing, so waHookKeyOk_ refused.

Fix. doGet checks hub.mode first and answers plain text:

function doGet(e) {
  if (e && e.parameter && e.parameter['hub.mode']) return waVerifyWebhook_(e.parameter);
  ...
}
function waVerifyWebhook_(p) {
  var token = PropertiesService.getScriptProperties().getProperty(WAH.VERIFY_PROP) || '';
  var ok = p['hub.mode'] === 'subscribe' && token && p['hub.verify_token'] === token && waHookKeyOk_(p.key);
  return ContentService.createTextOutput(ok ? String(p['hub.challenge'] || '') : 'forbidden');
}

Then Deploy → Manage deployments → edit → New version; copy URL and token (with the key) from the dialog.

How to verify. The 20.1 browser test returns exactly the challenge; the Node test asserts '42' for a good token and 'forbidden' for a bad one.

Prevention. Publish a new version after any doGet/doPost change; unit-test verification.

20.4 Secrets shown in tool output while reading Script Properties

Symptom. In a diagnostic session a tool read the Script Properties page and a helper that dumped all properties; token values appeared in clear text.

Cause. Project Settings displays property values and getProperties() returns them; any screen capture, browser automation or log then holds the secrets.

Fix. Rotate every exposed value (16.4): Meta token, dashboard key, webhook key/token. Diagnostics print names and presence only (16.3); token entry uses one box that confirms only the last four characters.

20.5 Draft regeneration ran out of memory

Symptom. bash go_master.sh regen stopped with "Memory limit of 512 MiB exceeded" (job email-sender-master, 512Mi).

Cause. generate_email() created a new OpenAI(...) client, with its own connection pool, per draft: invisible in a 5-minute run (at most 20 drafts per brand), fatal over hundreds.

Fix. One client per key per process, and bounded rounds:

_CLIENTS: dict = {}
def _client(runtime):
    from openai import OpenAI
    key = runtime.openai_api_key
    if key not in _CLIENTS:
        _CLIENTS[key] = OpenAI(api_key=key)
    return _CLIENTS[key]

regenerate.py has TIME_BUDGET_SECONDS = 22 * 60 (the run lock lasts 30 minutes); go_master.sh passes --limit,120 and loops up to 15 rounds while the log says Run the same command again to continue. Regeneration holds the run lock so nothing is sent from a half-changed row.

How to verify. bash go_master.sh sender, then bash go_master.sh regen: each round logs rewrote N, failed M, still old K, and K falls to 0.

Prevention. Expensive clients once per process; bulk jobs get a count limit, a time budget below the lock expiry, and are rerunnable.

20.6 The AI wrote "I didn't see any details about you"

Symptom. Drafts for leads with empty Details opened with "I didn't see any details about your business, but…", telling the reader they are on a list.

Cause. Two of the five opening styles asked for "one specific thing from the recipient details" or "a compliment specific to the details"; with nothing given, the model narrated the gap.

Fix. Three layers:

  1. DETAIL_OPENINGS = {0, 4} are used only when Details is filled (pick_brief).
  2. For empty Details, _input() adds: "Nothing is known about this recipient. Do NOT say that, do NOT mention details, a profile, their business or anything you 'saw' or 'noticed'… Write a short general note that fits anyone."
  3. SPAM_PHRASES includes "didn't see any details", "did not see any details", "no details", "your profile caught" (one rewrite, then Draft kept spam-risk wording).

How to verify. test_no_details_brief; no-details drafts read as short general notes.

Prevention. Back every prompt rule that matters with a code check and a test.

20.7 Website link in the signature hurt deliverability

Symptom. Early drafts ended with Website: https://www.<brand>.com/, and seed tests put more of them in spam.

Cause. Links in a first cold email from a new mailbox are a strong spam signal. The signature was added after the AI text, so the body check missed it.

20.8 Clearing 1,099 old drafts before 10:00 and resetting 19 Failed rows

Symptom. On 30 September, shortly before the 10:00 window, the owner asked that no old-format draft be sent. 1,099 queued rows still had old drafts (113 SB rows were rewritten on 29 September), and 19 rows were Failed.

20.9 Sheets API 502/503 during saves marked rows Failed

Symptom. Logs showed HttpError 502 or 503 from sheets.googleapis.com; some rows became Failed and a good draft was lost.

Cause. A short outage hit the save, and the broad except treated it as an AI failure.

Fix. execute_with_retry() in sheet_client.py retries reads and repeat-safe writes (get, update, batchUpdate values) on 429/500/502/503/504 and dropped connections, waiting 2, 5 and 10 seconds (four attempts). Appends are never retried, so no duplicate rows. In brand_runner._generate_drafts the AI call and the save have separate handlers:

try:
    sheets.batch_values([(f"'{tab}'!D{n}:F{n}", [[subject, body, "Generated"]]),
                         (f"'{tab}'!H{n}", [[""]])])
except Exception as error:
    # leave the row untouched so it is drafted again next run - never mark it Failed
    result.errors.append(f"row {n}: draft not saved ({type(error).__name__}); will retry")

How to verify. test_sheet_retry.py, including test_sheet_outage_does_not_mark_row_failed.

Prevention. Only "the work failed" belongs on the row, not "saving failed".

20.10 connect_gmail.sh EOFError

Symptom. After printing the sign-in link, the script crashed with EOFError: EOF when reading a line at the "paste the address" prompt.

Cause. The Python part runs from a heredoc (python3 - ... <<'PY'); its stdin is the consumed heredoc, so input() reads end-of-file.

Fix. Read answers from the terminal:

def ask(prompt):
    # stdin is this script's heredoc, so read the answer from the terminal itself
    print(prompt, end='', flush=True)
    with open('/dev/tty') as tty:
        return tty.readline()

How to verify. bash tools/connect_gmail.sh <address> waits for the pasted URL and saves the mailbox.

Prevention. Never use stdin for interactive input in heredoc-embedded programs.

21. Lessons learned

Most lessons are the Prevention notes of chapter 20; the cross-cutting ones:

  1. Meta webhooks have three levels; check webhook_configuration first (20.2).
  2. A saved Apps Script is not a deployed web app, and public URLs are configuration, not computed (20.1, 20.3, 20.16).
  3. Prompts are requests; code is a rule. Back every content rule, including "vary the structure" and "never narrate missing data", with code and a test (20.6).
  4. Separate "work failed" from "saving failed"; retry only what is safe to repeat (20.9).
  5. Bulk jobs: one client per process, a count limit, a time budget under the lock expiry, rerunnable, run under the lock (20.5, 20.8).
  6. Never overwrite people's data. Own columns only, re-read before writing, back up, never un-mark a reply.
  7. Secrets by name, never by value; rotate anything shown; errors show a secret's length, never its value (20.4, 20.19).
  8. Deploy with a dry run and print the rollback command; upload bundles to Cloud Shell (20.12).
  9. Not every failure is yours: upload media to Meta and explain 131049 plainly (20.14, 20.18).
  10. Safe defaults win: WhatsApp Off, mail emergency stop On, test mode On, mailboxes at Stage 1. Tests run in the build because CI did not.

25.2 The run algorithm

<run_algorithm>
One execution of `python main.py` (every 5 minutes, 10:00-17:55, Mon-Sat, India time), in order:
 1. Load RuntimeConfig and all enabled BrandConfigs. Flags:
      --brand <id>        only this brand (no rotation advance, no send-now queue)
      --dry-run           read everything, write nothing, send nothing
      --read-sheets       with --dry-run: read the live sheet (read-only client)
      --generate-only     drafts for one brand, never send (requires --brand, refuses --dry-run)
      --regenerate-drafts [--dry-run] [--brand] [--limit N]   (25.6)
 2. Run lock: Firestore document <collection>/run_lock, created in a transaction with {owner:
    hostname-uuid, locked_until: now + 30 min}. If locked_until is in the future, print
    "Another unified main.py run is already active. Exiting." and exit 0. Release it in a
    finally block, only if still the owner.
 3. Send-now queue first (not in dry-run, generate-only or --brand; 25.4). A queue failure is
    logged and printed; it never stops the scheduled work.
 4. Rotate BRAND_ORDER by Firestore round_robin.next_start_index so a different brand goes first.
 5. For each brand, BrandRunner.process() inside try/except (one broken brand never stops the
    others):
    a. Skip if disabled.
    b. Missing control, lead, send log or Do Not Contact tab -> "Missing required Sheet
       tab(s): ...", no writes.
    c. Settings from '<control_tab>'!A2:C10 by key (rows 2-10 as in 24.8); blank -> the
       config.json default.
    d. Read the Mail Log A2:I, mailbox rows A13:M60, leads A3:L and Do Not Contact A2:C.
    e. Merge sheet-added mailboxes into the sender list (with_sheet_mailboxes).
    f. Emergency stop = Yes -> stop this brand ("Emergency stop active").
    g. Write each mailbox's Sent today / Sent this hour (from the log) into F:G.
    h. Draft up to MAX_DRAFTS_PER_BRAND_PER_RUN rows (25.7) where can_generate(row): email
       present, subject or body blank, status not Sent, Unsubscribed or Bounced. Invalid email
       -> Skipped / "Invalid email address". If anything was drafted, re-read the leads.
    i. FIRST row (top to bottom) with Approve email = Yes and status in {Generated, Approved,
       Scheduled}. None -> "No approved lead is ready".
    j. Brand caps (max per day / hour, from Sent rows in the Mail Log, India time). Reached ->
       skip the brand this run.
    k. Newest Sent time + Minimum sending gap > now -> "Brand send gap active: N minute(s)
       remaining".
    l. Row checks, in order, each writing status F and reason H:
         invalid email            -> Skipped      "Invalid email address"
         blank subject or body    -> Scheduled    "Approved row has blank subject or body"
         in Do Not Contact        -> Unsubscribed "Recipient suppressed"
         already Sent by brand    -> Skipped      "Recipient already contacted by this brand"
         other brand, N days      -> Skipped      "Recipient recently contacted by another
                                                   brand" (only if CROSS_BRAND_DUPLICATE_DAYS>0)
         outside sending hours    -> Scheduled    "Outside sending hours"
         domain cannot get mail   -> Skipped      "Not sent: <reason> (would bounce)"
         no eligible mailbox      -> Scheduled    "No eligible mailbox"
    m. Dry run: add "Would send row N from X to Y; cc configured=True" and stop here.
    n. Send (failures: 25.5). On success write, in one batch:
         F:L = Sent, sent-at text, "" (clear error), mailbox, approval value (kept; "Yes" if
               blank), Gmail message ID, "Pending" (follow-up)
         B1  = the mailbox used (the tab's "From" line)
         Mail Log row: time, mailbox, lead, subject, message ID, "Sent", "", daily limit, stage
         Mail Control F:G +1, I:J = last sent at / next eligible time (now + gap),
         M = "Sent row N to <lead>"
       and record the send in Firestore successful_sends (recipient, brand, sender, sent_at,
       gmail_message_id) for the cross-brand check.
 6. At most ONE email per brand per run.
 7. Advance the round-robin index (not in dry-run or with --brand). Release the lock.
 8. Print per brand "<id>: processed=True generated=N sent=True/False skipped=<reason>
    errors=N", then dry-run notes and errors. These lines are what I read in the logs.
Times: every date written is text "yyyy-MM-dd HH:mm:ss" in India time. parse_datetime() also
reads "yyyy-MM-dd HH:mm", "dd/MM/yyyy HH:mm:ss", "dd-Mon-yyyy HH:mm" and ISO text.

25.5 Retries, statuses and failure semantics

<retries_and_failures>
Sheets API retries (sheet_client.execute_with_retry) wrap get, update, batchUpdate of values
and spreadsheets.get: retry HTTP 429, 500, 502, 503, 504, ConnectionError, TimeoutError and
OSError, waiting 2 s, 5 s, 10 s (4 attempts in total), then raise. Never retry values.append
(a retried append can add the same log row twice). Every write method raises "dry-run
blocked ..." when the client was created with dry_run=True.

Email status (F): blank = new, will be drafted; Generated = AI wrote D:E, waiting for J =
Yes; Approved = set by a person (optional; J = Yes counts); Scheduled = approved but held
for a temporary reason (hours, no mailbox, blank draft, reconnect), retried every run; Sent;
Skipped = will not be sent, H says why; Failed = AI or Gmail error, H says why; Bounced = set
by the report on Sent rows; Unsubscribed = in Do Not Contact. Replies are NOT a status (M:N).

Failure rules (exact; tests must prove each):
  AI call fails (no key, 401, 429, timeout, spam wording after one rewrite)
      -> F = Failed, H = "OpenAI generation error: <first 300 characters>". Drafted again on
         a later run (can_generate() excludes only Sent, Unsubscribed, Bounced). If writing
         that error also fails, ignore it.
  Draft generated but saving it fails after all retries
      -> row UNTOUCHED (no status, no error); run error "row N: draft not saved
         (<ErrorType>); will retry". Never mark it Failed (pitfall 9).
  Gmail refuses the mailbox (auth)   -> pause the mailbox, lead back to Scheduled (25.3).
  Gmail refuses the message          -> F = Failed, H = "Gmail API error <status>: <first 500
                                        characters>", Mail Log row Failed; mailbox not paused.
  Unexpected exception while sending -> F = Failed, H = "Send failed: <text>", Mail Log row.
  A whole brand raises               -> "<brand> failed: <error>" in the output; other brands
                                        continue; the lock is released.
  The report cannot read something   -> it still goes out with subject prefix "[PARTIAL] " and
                                        a red "Incomplete data" section (25.8).
Cell messages are short and plain. Never write a stack trace, token, key or full API response
into a cell, log line or report. For OAuth problems write "OAuth invalid_grant; mailbox needs
authentication repair", never the response body.

Resetting Failed rows (only when I ask): back up subject and draft to "Old drafts (backup)",
then clear only D, E, F and H of those rows so the next run redrafts them (pitfall 8).

Done when: test_sheet_retry.py proves the waits (2, 5, 10), the give-up after 4 attempts, no

     2 "Open with a one-line observation about a common challenge in their line of work, then

     3 "Open by saying plainly, in one short sentence, who you are and why you are writing to
        them specifically."
     4 "Open with a brief compliment that is specific to the recipient details (never generic
        praise)."

       influencers for their audience; making their paid ads spend work harder; keeping their

       next step that fits their situation
   Calls to action (5), each phrased "Ask if/who/what ...": a 10-minute call this week; send
     two or three relevant examples; who is the right person if not them; is this something
     they are looking at right now; what would make this worth a short conversation.
   Greetings with a first name (4): "Hi {name},", "Hello {name},", "{name},", "Hi {name}, hope
     your week is going well."  Without a name (3): "Hi there,", "Hello,", "Hi,"
   Length bands (body only): 60-80, 70-95 or 85-110 words.

   strip quotes, drop a trailing . ! ? :). Empty subject or body -> error.

   "You write short, personal first-contact emails for <brand_name>, one real person writing
